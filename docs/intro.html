§ 01

架构 · 一座洋葱

越靠内越通用,越靠外越定制
L1 · 业务装配层
code-reviewer / ops-bot · 各自的入口、生命周期、会话模型
L2 · 共享层
provider 注册 · 工具 · 合规拦截 — 跨产品复用
L3 · pi-mono 引擎
pi-coding-agent / pi-agent-core — 上游 npm 包,不 fork
L4 · 协议
pi-ai · LLM CORE

四层洋葱,各司其职

Flower 的核心思想是:越靠内的层越稳定通用,越靠外的层越业务定制。 通过这种分层,我们既能复用 pi-mono 生态的所有能力,又能让两个产品保留各自的形态。

  • L4 协议层:屏蔽不同 LLM 厂商差异,只关心消息和工具协议(Anthropic / OpenAI 兼容)。
  • L3 引擎层:agent loop / 事件流 / 工具注册 / skill 系统。直接用 npm 包,不 fork 上游。
  • L2 共享层:Flower 给两个产品的"通用配件箱"——provider、工具、合规拦截器。
  • L1 业务层:每个产品自己的入口形态(CLI vs HTTP)、生命周期、会话模型。

code-reviewer PIPELINE

// 一次性 · 无状态 · 跑完即退

  1. 1
    .gitlab-ci.yml 中 review job 由 MR / commit 触发
  2. 2
    docker run 启动评审容器,带入 $CI_MERGE_REQUEST_IID
  3. 3
    容器内 clone 项目并切到目标 commit
  4. 4
    pi -p "..." 启动 print 模式,LLM 自主用 read / grep 读代码
  5. 5
    通过 gitlab_post_comment / gitlab_post_line_comment 上墙
  6. 6
    有 severity === "blocker" 评论则 exit 1,pipeline fail

ops-bot WEBHOOK

// 长驻 · 有状态 · 流式回写

  1. 1
    钉钉群 @bot,webhook 推送到 HTTP server
  2. 2
    SessionStore 按 conversationId 从 Redis 取上下文
  3. 3
    Agent 自主决策:调 ARMS 工具 → 看结果 → 迭代
  4. 4
    订阅 message_update 事件,500ms 节流推送回钉钉
  5. 5
    完成后回写 Redis(24h TTL),触发 final 推送
  6. 6
    工具调用前经合规拦截器:权限校验 + 数据脱敏

pi-mono 是一座三层金字塔。

pi-mono 把"做一个 Agent"拆成了三件可独立使用的事:(1) LLM 协议适配、(2) 有状态 Agent 调度、(3) 终端 harness。每一层都是独立的 npm 包,可以单独使用, 也可以叠在上一层之上。

Flower 不是给 pi-mono 套个壳——而是分别站在不同的肩膀上: reviewer 用最高的 P3,直接复用 print 模式与 read/grep 工具; ops-bot 用中间的 P2,自己拼装 HTTP server 与会话存储。 两者都共享最底层的 P1。

"Adapt pi to your workflows, not the other way around, without having to fork." — pi-mono 哲学

Flower 当前锁定 @earendil-works/pi-* ^0.75.0, 通过 npm workspaces 统一管理。

EXT · 01
pi.registerProvider()
接入企业 LLM 网关

把内部自部署或企业 AI Gateway 注册为一个 provider,代码不变,接入即用。

EXT · 02
pi.registerTool()
注入领域工具

GitLab 工具(reviewer)与 ARMS 工具(ops-bot)分别注入到各自的 agent,无需改 pi 源码。

EXT · 03

挂载合规拦截器

事件订阅式拦截:写类工具禁用、bash 走白名单、ARMS 按 userId 鉴权、PII 脱敏全部在这里完成。

§ 03

同根不同枝

为什么是两个产品,而不是一个 Agent 平台

共享底座,但形态独立。

我们曾认真考虑过"一个 Agent 平台 + 多入口适配器"的方案。最终拒绝了—— 因为 CI/CD 和 webhook 服务的工程约束差异太大: 一个跑完即退、一个长驻 7×24;一个无状态、一个必须按用户隔离会话; 一个面向开发者的 MR 评论、一个面向全员的钉钉对话。

强行统一会让两边都被对方拖累。所以选择共享 70% 的"配件" (provider、工具、合规),但各自独立部署、独立进程、独立生命周期。 同根不同枝,各开其花。

§ 04

为什么这样设计

八组关键权衡 · 选了什么 · 拒绝了什么
Decision 01 · 引擎

用 pi-mono,不自己写 agent loop VS · 从零造轮子

Agent loop、事件流、工具协议、skill 系统、合规拦截这些本质都是基础设施, 不是业务价值。pi-mono 已经把这些做完了,我们只需要在外层装配。

放弃了完全控制权,换来 0→1 的速度与持续受益于上游改进
Decision 02 · 选型

reviewer 用 pi-coding-agent · ops-bot 用 pi-agent-core VS · 两边都用同一个

pi-coding-agent 假设"一个用户、一个进程、一个 TTY",自带 read / grep / bash, 天然匹配 CI 形态。pi-agent-core 是更底层的 Agent 类,适合自建 HTTP server + Redis 会话。各自选最合适的层级,而不是硬塞同一个。

需要理解两个上游 API,但避免了任何一方迁就另一方的扭曲
Decision 03 · 扩展

配置驱动,不 fork 上游 VS · 改源码 / 维护私有分支

LLM 接入通过 pi.registerProvider(),工具通过 pi.registerTool(), 行为通过 pi.on() 订阅事件修改。所有定制都在外层。 实在需要"换芯"时,用 npm overrides 做单包热插拔。

受限于上游扩展点的丰富度,但永远能跟上 upstream 演进
Decision 04 · 隔离

能力按产品隔离,不做"超级 Agent" VS · 一个 Agent 拥有所有工具

GitLab 工具仅 reviewer 加载;ARMS 工具仅 ops-bot 加载。 ops-bot 不应该有"写 GitLab"的权力,reviewer 也不该有"查监控"的权力。 职责隔离 = 权限隔离 = 故障域隔离。

放弃了"一个 bot 干所有事"的诱惑,换来权限边界的清晰
Decision 05 · 安全

CI 内的 Agent 必须只读 VS · 允许 LLM 自动改代码

通过 pi.on("tool_call") 全局拦截 write / edit, 并把 bash 限制在 git/grep/find 白名单。评审者不应是修改者—— LLM 给出建议,人类决定是否接受,这是责任边界。

放弃了"自动修复"的炫技,换来 100% 的代码安全感
Decision 06 · 体验

ops-bot 必须流式回复 VS · 同步等待结果

钉钉同步 webhook 5 秒超时,但运维查询常常需要 10s+。必须用钉钉的 sessionWebhook 流式机制:订阅 Agent 事件流,500ms 节流推送累积文本。 用户看到的不是"机器人在思考...",而是答案逐字浮现。

实现复杂度上升一档,但是用户体验的及格线
Decision 07 · 合规

LLM 走私有网关,数据在工具层就脱敏 VS · 直连公网 LLM API

代码可能涉密,ARMS 日志可能有 PII。两个原则:(a) 不走公网 LLM, 所有调用经企业 AI 网关;(b) 脱敏在工具层完成,LLM 永远看不到原始敏感数据 (它可能复述到回复里)。

放弃了直连最新公网模型的便利,换来合规的硬底线
Decision 08 · 责任

关键操作只建议,不执行 VS · Agent 自主重启服务 / 改配置

ops-bot 面向全员,如果 bot 给出错误的运维建议直接执行导致事故,谁担责? 所以所有 ARMS 工具都是只读,bot 只提供分析与建议, 操作权永远在人。同时按 userId 鉴权,不同人能看的也不同。

放弃了"全自动 SRE"的幻想,换来明确的人机责任边界
§ 05

未来愿景

在稳定的底座上能长出什么
底座已经具备"自规划"。当前 ops-bot 一次用户消息内,LLM 可自主调用任意多个工具, 基于结果迭代决策直到给出最终答案——这是 pi-agent-core agentLoop 的内建行为。 但这只是起点。下面六项能力,会把它从一个"被问才答的工具" 进化成一个主动观察、主动诊断、主动通知的 SRE 助手。
P0
能力 i.

Plan-then-Execute

面对复杂诊断时,LLM 先显式列计划再执行,边做边在 checklist 上打勾。 过程可观测,用户看清 bot 在干什么,LLM 也不容易漏步骤。

成本:低触发:诊断 / 根因 / 容量类
P1
能力 ii.

Diagnostic Sub-Agent

主 agent 把复杂任务派发给专项子 agent——更大的模型、更长的思考预算、专项 prompt。 简单查询走 mini 模型,复杂诊断升级。成本与质量动态平衡。

成本:中类型:diagnostic / capacity / cost
P2
能力 iii.

告警驱动 · 主动触发

监听 ARMS / 内部告警 webhook,告警发生时自动启动诊断, 把结论直接推送到对应钉钉群。从"被动问答"跨越到"主动 SRE"。

成本:中路径:alert → agent → 钉钉推送
P3
能力 iv.

定时巡检 · cron

定期让 agent 自主巡检关键应用,生成日报或健康度报告。 把"人工每天看一眼监控"自动化。与告警驱动共用基础设施。

成本:低注意:控制 LLM 调用频率与配额
P4
能力 v.

用户订阅 · Watcher

用户说"盯住 prod-app,RT 超过 200ms 告诉我",bot 后台持续监控, 触发条件后主动通知。把临时关注从用户脑子里移到 bot 里。

成本:高依赖:持久化 + 独立调度循环
P5
能力 vi.

持久化执行计划

长任务(如全链路压测后给报告)中途崩了能从断点恢复, 而不是从头跑。plan 存 Redis / DB,worker 启动时扫描未完成任务。

成本:高建议:有真实长任务需求时再做

B1

pi 框架深度分析

B1.1 API 表面(piMain / extension / Hook)

pi 对外暴露的「公开 API 表面」非常薄。reader 真正需要记住的只有四件:piMain 函数、extension 工厂类型、27 路 Hook 事件,以及 pi 内置的几个文件/Shell 工具。其它一切定制都在 extension factory 内部用 ExtensionAPI 完成。

piMain 函数签名

pi 的「主入口」是 main(args, options)(reviewer 里我们 import { main as piMain })。类型签名权威定义在 dist/main.d.ts,全文如下: 

import type { ExtensionFactory } from "./core/extensions/types.js";

export interface MainOptions {
    extensionFactories?: ExtensionFactory[];
}

export declare function main(args: string[], options?: MainOptions): Promise<void>;

两个关键观察:

  1. args 是字符串数组,等同于 CLI argv。reviewer 里 buildPiCliArgs 把 env 翻译成形如 ["-p", prompt, "--provider", "havefun-anthropic", "--model", "claude-opus-4-7", "--thinking", "high"] 的数组,然后传给 piMain。
  2. extensionFactories 是「函数注入」而非「路径注入」。flower 不往磁盘写 extension 文件,直接把 extension.ts 的 default export 函数引用传进来。

reviewer 的典型调用形态(见 flower-code-reviewer/src/run.ts § runReview): 

const piArgv = buildPiCliArgs({ prompt });
await piMain(piArgv, {
    extensionFactories: [extensionFactory],
});

piMain 的返回值是 Promise<void>——它不返回评审结果。LLM 输出 / 工具调用 / 评审动作全部通过 side effect 发生(extension 注册的事件 listener、注册的 tool execute 函数)。reviewer 看到 piMain resolve 后,所有评论已经通过 gitlab_post_line_comment 工具发到了 GitLab,再走自己的 scanForBlockers 决定 exit code。

extension 工厂类型

ExtensionFactory 是 pi 整个定制体系的根契约,签名极简(dist/core/extensions/types.d.ts): 

export type ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>;

factory 是一个普通函数,拿到一个 ExtensionAPI 实例后,在体内调 pi.registerTool / pi.registerProvider / pi.on(event, handler) / pi.registerCommand 等方法。同步或异步均可;返回 Promise 的话,pi 会 await 它再继续 startup(意味着「provider 远端模型列表加载」之类的异步初始化可以在这里完成)。

ExtensionAPI 暴露的方法粗分两类:

  • 注册类(改 pi 的能力):registerTool / registerProvider / registerCommand / registerShortcut / registerFlag / registerMessageRenderer
  • 订阅类(挂事件 listener):pi.on(event, handler) 共 27 路重载(下一小节详述)

Hook 事件总线(27 路 pi.on)

Hook 是 pi 对外开放的核心定制点。ExtensionAPI.on 是 27 路重载方法,每条 event 都有强类型 payload 和可选返回值。reader 不需要背全部 27 路,但要知道按生命周期分成几大类:

会话级
session_start / session_shutdown / session_before_switch / session_before_fork / resources_discover 等(6 路)
agent 级
input / before_agent_start / agent_start / agent_end(4 路)
turn 级
turn_start / turn_end / context / before_provider_request / after_provider_response(5 路)
message 级
message_start / message_update / message_end(3 路)
tool 级
tool_execution_start / tool_call / tool_execution_update / tool_result / tool_execution_end(5 路)
模型与命令
model_select / thinking_level_select / user_bash(3 路)

handler 类型统一为: 

export type ExtensionHandler<E, R = undefined> =
    (event: E, ctx: ExtensionContext) => Promise<R | void> | R | void;

关键观察:

  • handler 同时支持 sync 与 async(Promise<R | void> | R | void)。
  • 部分 event 的返回值有控制语义:tool_call 返回 { block: true, reason?: string } 可阻塞工具执行;context 返回 { messages } 可替换 LLM 上下文;message_end 返回 { message } 可替换 finalized message。返回 void 默认无影响,适合「只观察、不干涉」的 listener(reviewer 的 review-trace 就是这种)。
  • 多个 handler 监听同一个 event 时,按注册顺序触发,这是 flower extension 中 compliance 先于 review-trace 注册的关键依据。

ToolCallEvent 是个联合类型,内置 tool(bash / read / edit / write / grep / find / ls)有强类型 input,自定义 tool fallback 到 Record<string, unknown>: 

type ToolCallEvent =
    | BashToolCallEvent | ReadToolCallEvent | EditToolCallEvent | WriteToolCallEvent
    | GrepToolCallEvent | FindToolCallEvent  | LsToolCallEvent   | CustomToolCallEvent;

interface CustomToolCallEvent {
    type:       "tool_call";
    toolCallId: string;
    toolName:   string;
    input:      Record<string, unknown>;
}

内置工具:read / bash / edit / write 接入点

pi 内置 7 个文件/Shell 工具,启动时按 --tools allowlist 选择性注册:

  • read——读文件(带行号偏移、limit、二进制兜底)
  • edit——按 old_string/new_string 精确替换
  • write——整文件重写
  • bash——执行 shell 命令(支持 background / timeout / cwd)
  • grep / find / ls——文件系统导航

每个内置工具都暴露可替换 operations 接口(createReadTool({ operations }) 之类)。这意味着 extension 可以接管 pi 的文件/Shell 后端——例如把 read 改成「读远端 SSH 沙箱」、把 bash 改成「在 Docker 容器里跑」。flower 当前没有替换内置工具,reviewer 跑在 CI runner 里,直接用本地 ops。

extension 也可以注册同名 tool 覆盖内置,或注册全新自定义 tool。pi 文档 § Overriding Built-in Tools 给出了详细范式;flower 走的是「不覆盖内置 + 加自定义 GitLab/合规工具」的方式。

B1.2 内部运作机制(turn loop / tool dispatch / event)

API 表面只是 pi 给 extension 的「接缝」;真正决定一个评审跑起来长什么样的,是 pi 内部把这些接缝串成的生命周期机制。本节按四层展开:turn loop 序列 / event 系统 / tool dispatch 7 步 / extension factory lifecycle。

turn loop 序列(核心生命周期)

pi 把生命周期切成 5 层,从外到内:session(会话开关 + tree fork / compact) → agent(一次用户 prompt 产生的一段处理) → turn(一轮 LLM 响应 + 该轮里的 tool calls) → message(单条 assistant / user / toolResult 消息) → tool execution(单次工具调用)。完整 lifecycle 来自官方 docs/extensions.md § Lifecycle Overview: 

pi starts
  │
  ├─► session_start { reason: "startup" }
  └─► resources_discover { reason: "startup" }
      │
      ▼
user sends prompt ─────────────────────────────────────────┐
  │                                                        │
  ├─► (extension commands checked first, bypass if found)  │
  ├─► input (can intercept, transform, or handle)          │
  ├─► (skill/template expansion if not handled)            │
  ├─► before_agent_start (can inject message, modify sys)  │
  ├─► agent_start                                          │
  ├─► message_start / message_update / message_end         │
  │                                                        │
  │   ┌─── turn (repeats while LLM calls tools) ───┐       │
  │   │                                            │       │
  │   ├─► turn_start                               │       │
  │   ├─► context (can modify messages)            │       │
  │   ├─► before_provider_request (inspect/replace)│       │
  │   ├─► after_provider_response (status, headers)│       │
  │   │                                            │       │
  │   │   LLM 响应,可能产生 tool call:             │       │
  │   │     ├─► tool_execution_start               │       │
  │   │     ├─► tool_call (can block)              │       │
  │   │     ├─► tool_execution_update              │       │
  │   │     ├─► tool_result (can modify)           │       │
  │   │     └─► tool_execution_end                 │       │
  │   │                                            │       │
  │   └─► turn_end                                 │       │
  │                                                        │
  └─► agent_end                                            │
                                                           │

每轮 turn 包含「一次 LLM 调用 + 该次返回的 tool calls 全部跑完」。如果 LLM 那一轮没调 tool(直接给最终答案),turn 就只有一次 LLM 请求,然后 turn_end。如果调了 3 个 tool,turn 内部就跑 3 次 tool execution,然后 turn_end,接着可能进入下一个 turn(LLM 用 tool 结果继续推理)。reviewer 在中等长度评审任务里通常 2–6 个 turn,LLM 在每个 turn 里调 1–4 个工具。

pi 默认是并行 tool 模式(parallel mode):一个 assistant message 里有多个 tool call 时,tool_execution_start 在 preflight 阶段按 source order 全部 emit,但 tool_call / tool_execution_end 可能在多个 tool 间交叉 emit(各 tool 完成顺序不定)。

event 系统:27 路 pi.on 关键事件 + payload

flower observability 监听了 6 类核心 event,reader 通过它们就能看到 LLM 在 GitLab CI 日志里的完整轨迹。下表把每路 event 的payload 形状和 flower 的使用方式对照列出:

turn_start
{ type, turnIndex, timestamp }。flower 打 >>> 🤖 [turn N] start。
message_update
{ type, message, assistantMessageEvent }。assistantMessageEvent 是流式 token 子事件(thinking_start / thinking_delta / thinking_end / text_start / text_delta / text_end / toolcall_end 等),来自 @earendil-works/pi-ai 的 AssistantMessageEvent 类型。flower switch 这些子类型把 LLM 的思考 / 输出 / 工具决定流式打印出来。
tool_execution_end
{ type, toolCallId, toolName, result, isError }。flower 打 🔧 [tool ←] 或 🔧 [tool ✗ error],result 截断 300 字符防日志爆炸。
after_provider_response
{ type, status, headers }。flower 在 status >= 400 时打 ⚠️ [llm provider] status=NNN(提前提示 LLM 网关异常,reviewer 后续会走 E1 fail-open)。
turn_end
{ type, turnIndex, message, toolResults }。flower 打 >>> 🤖 [turn N] end · toolResults=K。
agent_end
{ type, messages }。print 模式下 agent_end 后整个进程退出。flower 打 >>> 🤖 [agent] session end。

另有一条 tool_call 事件,flower 在 extension.ts 中专门为 review-trace 注册了 listener,只观察不阻塞(返回 undefined),只对 gitlab_get_file_content 累加 readFiles、对 gitlab_post_line_comment 累加 lineComments,供 reviewer_list_my_blockers 工具读取本轮 blocker 真值。

tool dispatch 7 步序列

LLM 在某个 turn 的 message 里包含 tool_call blocks 时,pi 内部按以下 7 步处理(从 dist/core/extensions/runner.d.ts 的 emitToolCall / emitToolResult 等签名 + 官方 lifecycle 图对照反推): 

1. emitToolExecutionStart(toolCallId, toolName, args)
   ↓  通知 listener,UI / 流式输出显示工具卡片

2. emitToolCall(event)
   ↓  给 extension hook 拦截机会(按注册顺序逐个 await handler)
   │  ├─ 任一 handler 返回 { block: true, reason } → 跳到步骤 6,result = "Blocked: <reason>"
   │  └─ 任一 handler mutate event.input → 改后的 input 传给 execute

3. dispatch:lookup tool registry by name → 调对应 execute(toolCallId, params, signal, onUpdate, ctx)
   ↓  ├─ 内置 tool:走 createReadTool / createBashTool 等的内部 ops
   │  └─ extension tool:走 pi.registerTool 传入的 execute(reviewer 走这条)

4. 执行过程中可能多次 onUpdate(partialResult)
   ↓  emit tool_execution_update(部分 tool 有流式中间结果,如 bash 长输出)

5. execute 返回 AgentToolResult
   ↓  emit tool_result(可被 handler 修改 content / details / isError)

6. emit tool_execution_end(result, isError)
   ↓  此时所有 listener 都拿到结果

7. result 作为 toolResult message 进入 LLM 上下文
   ↓  等下一个 turn 用

关键设计点:

  • extension 注册的 tool 与 pi 内置 tool 共用同一个 dispatch 表。extension 可以注册同名 tool 覆盖内置(docs/extensions.md § Overriding Built-in Tools)。
  • 多个 pi.on("tool_call", ...) handler 按注册顺序逐个 await(docs/extensions.md § tool_result 明示 handlers run in extension load order,tool_call 同样行为
    ~推测,以源码为准~
    )。这是 flower 把 compliance 放在 review-trace 之前注册的根本依据 — 让合规拦截先于 trace 记录决定是否放行。
  • handler 链中任一返回 { block: true } 即停止后续 handler 调用、跳过 execute、直接拼一个错误 toolResult 给 LLM。flower compliance 在 ci-readonly 模式下用这个机制禁掉写工具与未授权 bash 命令。

extension.ts 全文 dump

/**
 * code-reviewer 的 pi 扩展
 *
 * 调用顺序很关键:
 * 1. 先注册 LLM provider —— 没这一步,pi 找不到模型
 * 2. 再注册合规拦截 —— 这是后续工具调用的"门禁"
 * 3. 最后注册业务工具 —— GitLab + 通用工具 + reviewer 自审工具
 * 4. 最后挂 tool_call trace 监听器(N1:用于「无依据评论」blocker 拦截 +
 *    v2:用于 reviewer_list_my_blockers 收集本轮 blocker 真值)
 */

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { registerCompliance } from "@flower-ai/flower-compliance";
import { registerHavefunProviders } from "@flower-ai/flower-providers";
import { registerCommonTools } from "@flower-ai/flower-tools-common";
import { registerGitlabTools } from "@flower-ai/flower-tools-gitlab";
import { registerObservability } from "./observability.js";
import { recordFileRead, recordLineComment } from "./review-trace.js";
import { registerReviewerSelfTools } from "./reviewer-self-tools.js";

/**
 * 注册 code-reviewer 所需的全部能力
 */
export default function (pi: ExtensionAPI): void {
    registerHavefunProviders(pi, { appSource: "code-reviewer" });
    registerCompliance(pi, { mode: "ci-readonly", product: "code-reviewer" });
    registerCommonTools(pi);
    registerGitlabTools(pi);
    registerReviewerSelfTools(pi);
    registerReviewTrace(pi);
    registerObservability(pi);
}

/**
 * 把 LLM 的工具调用追踪到 review-trace,供 run.ts finalize 阶段做「无依据评论」检查,
 * 以及 `reviewer_list_my_blockers` 工具读取本轮 blocker 真值
 *
 * 监听两个工具:
 * - `gitlab_get_file_content` → 累计 readFiles
 * - `gitlab_post_line_comment` → 累计 lineComments(含 severity + 抽取的 title)
 *
 * 注:本监听器**不**阻塞工具(不返回 `{ block: true }`),只观察;阻塞由 compliance 负责。
 */
function registerReviewTrace(pi: ExtensionAPI): void {
    pi.on("tool_call", async (event) => {
        if (event.toolName === "gitlab_get_file_content") {
            const path = event.input.path;
            if (typeof path === "string") {
                recordFileRead(path);
            }
            return undefined;
        }
        if (event.toolName === "gitlab_post_line_comment") {
            const file = event.input.file;
            const line = event.input.line;
            const severity = event.input.severity;
            const body = event.input.body;
            // 四字段类型守卫(防御 LLM 异常输入 / schema 不匹配):
            // 缺任一字段都不记录,避免后续 reviewer_list_my_blockers 返回脏数据
            if (
                typeof file === "string" &&
                typeof line === "number" &&
                (severity === "blocker" || severity === "major" || severity === "minor") &&
                typeof body === "string"
            ) {
                recordLineComment({ file, line, severity, body });
            }
            return undefined;
        }
        return undefined;
    });
}

注册顺序的「为什么」

factory 主体 7 行调用,每一行的顺序都是有意为之。表面看每一项都互不相关,实际上它们组成了一条依赖链:

① providers
registerHavefunProviders 必须第一个调。没有 provider,pi 在解析 CLI argv --provider havefun-anthropic --model claude-opus-4-7 时会找不到模型,直接抛错——后面的注册都白搭。
② compliance
registerCompliance 次之。它通过 pi.on("tool_call", ...) 注册了「门禁拦截器」。pi 触发 tool_call 事件时按 handler 注册顺序逐个 await,所以 compliance 必须比业务工具的 trace listener 先注册,确保「先拦截、再观察」。
③ 业务工具
三行业务工具调用(registerCommonTools / registerGitlabTools / registerReviewerSelfTools),给 LLM 真正能用的能力:6 个 GitLab REST 工具 + 通用 stub(禅道 / 钉钉文档搜索)+ reviewer 自审工具(reviewer_list_my_blockers 等)。注册先后顺序在这里无强制要求,只是惯例上「跨产品共享」放最前、「特定产品」放最后。
④ trace
registerReviewTrace 倒数第二个。它和 compliance 一样监听 tool_call,但只观察(不返回 { block: true })。这两者共用 tool_call 事件链,顺序决定语义:compliance 先看,可能拦截;trace 后看,只看「通过的工具调用」。
⑤ observability
registerObservability 最后调,它监听 turn / message / tool 一堆 event,做 stdout 流式打印——属于「打印旁路」,不参与决策,因此放最后没有副作用。

flower-providers 注册 4 个 havefun-* provider + flush 机制

registerHavefunProviders(在 packages/flower-providers/src/register.ts 内)给 pi 一次性注册四个 provider:havefun-openai / havefun-openai-responses / havefun-anthropic / havefun-gemini。每个 provider 的模型按 nativeApi 严格归属——内置 8 条模型,每条只挂在对应 nativeApi 的那一个 provider 下,杜绝 pi 内部按重名 model id 误选。

如前一节(B1.2 § extension factory lifecycle)所述,extension factory 阶段调 pi.registerProvider(...) 时,注册项会被排队到 pendingProviderRegistrations,在 ExtensionRunner.bindCore() 执行时统一 flush 到 ModelRegistry。这意味着 reviewer factory 跑完(7 行 register 调用)后,4 个 provider 是「已排队待 flush」状态;直到 pi 准备好开始第一个 turn 之前,所有 provider 才正式可见——这是 pi 显式设计的事务式注册。

另一个细节:apiKey 字段传的是 env 变量名(FLOWER_HAVEFUN_API_KEY),不是字面 key。pi 内部用 AuthStorage 解析,优先读 auth.json,然后 fallback env(docs/sdk.md § API Keys and OAuth)。这套机制让 reviewer 在 GitLab CI 容器里可以纯走 env 注入,不需要写任何 secret 文件到容器盘。

pi 的定位:核心薄、extension 厚

Pi is aggressively extensible so it doesn't have to dictate your workflow.

Custom tools (or replace built-in tools entirely) · Sub-agents and plan mode · Custom compaction and summarization · Permission gates and path protection · Custom editors and UI components · Status lines, headers, footers · Git checkpointing and auto-commit · SSH and sandbox execution · MCP server integration · Make pi look like Claude Code · Games while waiting (yes, Doom runs)

  4. pi 升级风险。pi 在快速迭代(CHANGELOG 一周一次 patch);extension API 在 1.0 之前可能小幅 break。flower 用 npm ^0.75.3 允许 minor 升级,需要在升级时跑一遍 reviewer regression。

cli.ts · 进程入口 + ESM guard + exit code 转发

做什么:#!/usr/bin/env node shebang;main() 调 parseArgs + runReview,然后 process.exit(result.exitCode)。exit 1 前调 formatExit1Notice 打一行预告日志,让 trace 读者知道 Runner 后续显示的 "Job failed" 是 reviewer 设计层面的门卫信号(发现 blocker 主动 exit 1),不是脚本崩溃。

顶层 catch-all:main().catch((err) => { console.error("[code-reviewer] 运行失败:", err); process.exit(2); }) — 任何未在 runReview 内被吸收的 throw 都转 exit 2(配置错 / GitLab API 错 / 真实 bug)。

§ 工作流程(7 步)

## 工作流程

1. 先调用 `gitlab_get_previous_review` 看自己之前在本 MR 发过哪些评论,**不要重复**。
2. 调用 `gitlab_get_mr_files` 看修改了哪些文件。
3. 调用 `gitlab_get_mr_diff` 看完整 diff。
4. **每个变更文件**:必须调用 `gitlab_get_file_content` 拉当前可读取窗口。
   - **看 MR source 版本**(评审主路径):`ref` 参数**必须传** `"${input.sourceBranch ?? "<MR source branch — env CI_MERGE_REQUEST_SOURCE_BRANCH_NAME>"}"`(本 MR 当前 source branch),不要省略也不要传 `"HEAD"`
   - **看 target 版本 / 历史 commit**:显式传 branch 名 / commit sha
   - 工具对 `"HEAD"` / 空字符串 / 缺省会兜底到 source branch 并 warn 教育,**主动正确传值**避免噪音
5. 必要时再调用 `gitlab_get_file_content` 拉**相关上下文**(被改函数实现 / 被改类定义 / 调用方)。
6. 对每个有问题的地方,调用 `gitlab_post_line_comment` 发行内评论。
7. **校对本轮 blocker 真值(强制)**:发完所有 line_comment 后,**必须**调用一次
   `reviewer_list_my_blockers`(无参),拿到本轮你刚发的 blocker 列表 `{count, blockers:[{path,line,title}]}`。
   这是写下一步 walkthrough alert 块的**唯一真值**,**严禁**靠对话历史记忆数。
8. 全部评审完后,如有总结性意见,调用 `gitlab_post_comment` 发整体评论。
   - 若步骤 7 拿到 `count >= 1`:walkthrough 顶部**必须**插入 `> [!caution]` alert 块(GitLab 17.10+)
     或降级 `> ⚠️ **Caution**` blockquote(< 17.10),其中:
     - **N 数字** = 步骤 7 的 `count`(不允许靠记忆数)
     - **Blocker 列表** = 步骤 7 的 `blockers` 数组,**逐条照抄**为 `- \`<path>:<line>\` — <title>`,
       **不允许**摘要 / 漏列 / 增列 / 改字面值 / 调整顺序
   - 若步骤 7 `count === 0`:**不要**插入 alert 块(沿用"无 blocker 不插 caution"约定)
虽然 prompt 内说"7 步",但实际编号 1-8 — 第 7 步是 2026-05-21 walkthrough 一致化 v2 加的"调 reviewer_list_my_blockers 拿真值"硬约束,把原来"步骤 6 发完评论直接写 walkthrough"拆成"6 发 / 7 拿真值 / 8 用真值写 walkthrough"三步,所以编号比"7 步"多 1。沿用 PRD 习惯仍称 7 步工作流。

§ 严格要求

## 严格要求

- **所有意见必须通过工具发表,不要在文本输出里给意见**。CI 日志没人看。
- severity 仅在以下情况打 `blocker`:
  - 安全漏洞(SQL 注入、XSS、敏感信息泄漏等)
  - 明显的逻辑错误会导致生产事故
  - 不符合团队/项目的硬性合规要求
- 风格 / 命名 / 建议性问题打 `major` 或 `minor`。
- 评论要给出**具体修改建议**,不要只说"这里不好"。
- 不确定的地方,宁可不发,不要发错的。${dryRunHint}

dryRunHint 在 input.dryRun === true 时拼为「注意:当前是 dry-run 模式,请仍然输出你打算发的评论(转 stdout),但不要调用 gitlab_post_* 工具。」,否则为空字符串。

§ 工具优先级(强制)

## 工具优先级(强制)

- **MR / 文件 / 代码信息**:首选 `gitlab_*` 工具,**不要**用 bash 兜底
  - MR 文件列表 → `gitlab_get_mr_files`
  - MR diff → `gitlab_get_mr_diff`
  - 文件全文 → `gitlab_get_file_content`
  - 历史评论 → `gitlab_get_previous_review`
- **bash 用法**:
  - ✅ 可用:`git` 系列(log / show / diff / blame / branch …)
  - ✅ 可用:搜索(`grep` / `rg` — 推荐 `rg`,更快 + 自动跳 `.gitignore`)
  - ✅ 可用:文本处理(`sed` / `awk` / `sort` / `uniq` / `tr` / `nl` / `column` / `printf` / `echo` 等)
  - ✅ 可用:路径 / 元信息(`pwd` / `basename` / `dirname` / `realpath` / `date` / `which`)
  - ❌ **禁用**:`env` / `printenv`(可能泄漏 secret)
  - ❌ **禁用**:`curl` / `wget` / `nc`(网络外发)
  - ❌ **禁用**:任何写文件命令(`mv` / `rm` / `tee` / `cp` 等)
- bash 不在白名单内会被 compliance 拦截(reason 附带替代建议),浪费一轮 turn,**先看本段再用**

§ 评论 markdown 样式(强制 · 8 条规则)

## 评论 markdown 样式(强制)

1. **行内评论(gitlab_post_line_comment)**必须按 4 段式:
   - 第 1 行:`<emoji> **<等级 中文>** <一句话问题标题>`(纯 emoji + 加粗等级即可,**不要**写 `[severity:*]` 字面 marker)
     - level ∈ {blocker, major, minor},分别对应 emoji + 中文等级:🔴 **阻塞** / 🟠 **重要** / 🔵 **建议**
     - 例:`🔴 **阻塞** 硬编码 secret 泄漏风险`
   - 第 2-4 行:解释段落,1-3 句,讲 why(diff 已经在 GitLab UI 显示了 what)
   - 折叠区 1(可选):`<details><summary>修复建议</summary>` 包 ` ```suggestion ` 块
   - 折叠区 2(可选):`<details><summary>推理过程</summary>` 包 reasoning,默认折叠避免刷屏

2. **整体评论(gitlab_post_comment)**用 walkthrough 结构,**整个 body 包在 `<details>` 里默认折叠**:
   - `## 概要`(2-3 句变更总览)
   - `## 文件变更`(表格:文件路径 | 一句话总结 | 关注等级)
   - `## 行动建议`(任务列表,如有 blocker)
   - 不要生成 emoji 诗

3. **「无问题」轻量评论**:只发一条整体评论,正文 ≤ 3 行,不折叠:
   ```
   :white_check_mark: 已审,未发现需要修改的问题。
   <一句话补充,如关注的点或值得肯定的实现>
   ```

4. **GitLab quick action 禁令**:绝对不要生成以 `/` 开头的整行(如 `/approve` `/close` `/assign`),
   GitLab 会把它当 quick action 真的执行。如果评论中需要展示路径,用反引号包(`` `/path/to/file` ``)。

5. **emoji 用 GLFM 兼容的 shortcode**(`:warning:` 而不是原生 ⚠️),便于 GitLab 自定义 emoji 渲染。
   例外:severity 行的 🔴/🟠/🔵 用 unicode 直接写(GitLab/GitHub 都直接渲染)。

6. **severity 等级表达**:行内评论第 1 行用 emoji + 加粗中文等级(🔴 **阻塞** / 🟠 **重要** / 🔵 **建议**)表达,
   **不要**写 `[severity:*]` 字面 marker。blocker 评论的机器可读 marker 由 `gitlab_post_line_comment` /
   `gitlab_post_comment` 工具自动以 HTML 注释形式注入(用户看不到),不需要你在 body 里手写。
   只对真问题打 blocker(参考现有规则)。

7. **真实代码上下文约束**(Phase 2 N1):对 MR 改动的**每个变更文件**,必须先调用
   `gitlab_get_file_content`(`ref` 显式传 `"${input.sourceBranch ?? "<MR source branch>"}"`,
   **严禁**传 `"HEAD"` / 空字符串 / 省略)拉当前可读取窗口再发出评论。
   鼓励主动拉**相关上下文**(被改函数实现 / 被改类定义 / 调用方),用 `gitlab_get_file_content`
   传任意 ref 和路径即可。
   **未拉文件直接发该文件的行内评论 → 视为「无依据评论」 → `scanForBlockers` 会拦截为 blocker
   (自我阻塞)**。
   你可以重复读同一文件(client 内部已防重复请求),但**不能跳过读取**。

isLlmFailure 五级判定决策树

这是 E1 fail open 的核心判定 — 区分 "LLM 网关挂了"(可 fail open)与 "GitLab API 错 / 真实 bug"(必须 fail close)。规则按优先级短路:

err 进入 isLlmFailure(err)
  │
  ├─【1】err instanceof AuthError ? ──── yes ──▶ return false (GitLab token 错)
  │       │ no
  │       ▼
  ├─【1】err instanceof FileNotFoundError ? ─ yes ─▶ return false (GitLab 文件 404)
  │       │ no
  │       ▼
  ├──────  err instanceof Error ? ──── no ──▶ return false (非 Error 对象,保守 fail close)
  │       │ yes
  │       ▼
  │   message = err.message.toLowerCase()
  │   errorName = err.name.toLowerCase()
  │       │
  ├─【2】 message / name 含以下任一关键字?
  │       llm / provider / anthropic / openai / gemini /
  │       model / stream / completion / havefun
  │       │ yes ──────▶ return true  (LLM / provider 显式失败)
  │       │ no
  │       ▼
  ├─【3】 message / name 含以下任一关键字?
  │       econnrefused / etimedout / aborterror /
  │       timeout / fetch failed / network
  │       │ yes ──────▶ return true  (网络 / 超时 — 保守认为是 LLM 调用阶段)
  │       │ no
  │       ▼
  ├─【4】 message 匹配 /\b5\d\d\b/ ?  ── yes ─▶ return true  (HTTP 5xx)
  │       │ no
  │       ▼
  ├─【4】 message 匹配 /\b429\b/ ?     ── yes ─▶ return true  (限流)
  │       │ no
  │       ▼
  └─【5】 默认                              ──▶ return false (fail close,避免吞真实 bug)

设计取舍:

  • 第 1 级 GitLab 错误类显式黑名单:这两个错误已经能精确识别(instanceof),不是 LLM 问题,直接 fail close 让 cli.ts catch 转 exit 2;
  • 第 2-4 级 关键字白名单:LLM SDK / provider / 网络 / HTTP 状态相关都允许 fail open;
  • 第 5 级 默认 fail close:不在白名单 = 不确定,宁可 exit 2 报错也不要吞掉真实 bug。
isLlmFailure 是保守 + 经验式判定;piMain 抛错的形态不固定(可能是 SDK Error / 自定义类),用 message 关键字 + GitLab 错误类黑名单兜底。未来踩到边界 case 再细化(例如某些 provider 抛 "Forbidden" 不带 LLM 关键字,会被错判为 fail close;触发后加进白名单即可)。

Dockerfile 关键步骤(两阶段构建)

第 1 阶段 · builder(node:22-alpine AS builder):

observability 这条流是完全旁路的:reviewer 监听 pi 内部 6 个事件(turn_start / turn_end / message_update / tool_execution_end / after_provider_response / agent_end),把内容截断后写 stdout,在 GitLab CI 日志里就能看到 LLM 的 thinking / text / tool call / error。handler 不返回 { block: true },不影响主流程;FLOWER_VERBOSE 默认开,设为 0 / false / off / no / 空字符串才关。

关键 trade-off

默认开,显式关(FLOWER_VERBOSE 黑名单语义):FLOWER_VERBOSE 未设 / 不在黑名单 = 开;只有显式设为 0 / false / off / no / 空字符串才关。业务方零配置就能在 GitLab CI 日志里看到 LLM 的 thinking / text / tool call,debug 友好。

截断防 GitLab CI 日志爆炸:truncate(value, max=400) 默认 400 字符,tool_execution_end 用更短的 max=300(工具结果可能含 MR 整文件 diff,容易爆量)。safeReadFile 在工具层已截断到 50KB,observability 再加一层防御 — 双层 cap 在不同层级抓不同体量的爆点。

纯只读不阻塞,异常被 pi 吃:handler 全部 return void(不返回 { block: true }),旁路写 stdout。回调内部如果 await 抛错,pi 会吃掉异常 — observability 失败不连坐主流程。这也意味着 observability bug 无法被 reviewer 退出码暴露,本地调试时需要 FLOWER_VERBOSE=1 + 直接 tail stdout。

after_provider_response 仅在 status ≥ 400 打:正常 200 不打,只在异常时 warn 一行 — 不刷屏。这与 B3.1 的 isLlmFailure 路径形成双重指示:CI 日志里看到 ⚠️ [llm provider] status=429 这种行,基本能预判 reviewer 会 fail-open(LLM 网关限流类错误);而 isLlmFailure 在 catch 路径里做最终判定,两者互证。

stdout 直接 write(无 buffer):thinking / text 是 process.stdout.write(ev.delta) 而非 console.log — 流式 token 需要立刻 flush 出来看打字效果,console.log 会自带换行 + 可能被 Node 内部 buffer 延迟。

B3.4 SIEM 审计:compliance 拦截 → POST SIEM_INGEST_URL

三类事件 fire-and-forget 上报:fail-open + 2s 超时 + 只上报字段名不上 value

关键 trade-off

fail-open 设计:sendAudit 失败默认静默。SIEM 抖动(网关挂、网络断、URL 写错)不反向定罪 reviewer,reviewer 不会因 audit 失败 fail pipeline;DEBUG_AUDIT=1 才打 warn 用于本地调试。代价是 SIEM 数据完整性不保证 — 但这是审计场景的标准取舍:可达即丢比反向阻塞业务更优。

2s 超时上限:AbortSignal.timeout(2000) — 不拖慢主流程。reviewer 单次 turn 已经 10-30s 量级,如果 SIEM 网关挂掉每次 audit 等 30s 就会让整体超时;2s 是经验值:够覆盖正常 RTT,又不至于在网络故障时拖累 reviewer。

不上传 input value 全量,只上报字段名:registerAudit 只上报 inputKeys: Object.keys(event.input ?? {})(比如 ["body","severity","file","line"]),不上传 value。理由:input.body 可能含未脱敏代码片段 / LLM reasoning,不同企业 SIEM 合规域差异大(GDPR / PII / 商业秘密),保守不上 value;真要看到完整 input,运维需要拿 GitLab CI log + debug 模式两边对齐。

session_start / tool_result 不可阻塞,纯通知:pi.on("session_start", ...) / pi.on("tool_result", ...) 在 pi 类型上没有 result 类型,handler return 直接被忽略 — 纯通知事件,与 tool_call(可 block)语义不同。这意味着 audit 只能在这两个事件上"事后旁观",不能拦。

production-readonly 模式同样开启 audit:registerCompliance 不管 mode 是 ci-readonly 还是 production-readonly 都调 registerAudit,只是 ci-readonly 额外开启 registerCiReadOnlyGuards。ops-bot 用 production-readonly — 工具本身已只读(不触发拦截),只产 audit 流,SIEM 上的 tool_call / tool_result 记录就能追溯"哪个用户、哪台 host、调了什么钉钉 / 钉群操作"。

附加 user + host 字段用于追责:sendAudit 在 body 上拼 user: process.env.USER ?? USERNAME ?? "unknown" + host: process.env.HOSTNAME ?? "unknown"。GitLab CI 环境对追责"哪个 job 在哪台 runner 跑"还有价值;本地开发对应开发者 username + 机器名。这两个字段不来自 reviewer 业务逻辑,而是 audit 这一层自己补的"环境身份"。

⚠️ 隐含行为:被 ci-readonly 拦截的 tool_call 不会被 audit。 原因:registerCompliance 内部先调 registerCiReadOnlyGuards(拦截 handler 先 pi.on("tool_call", ...) 注册),再调 registerAudit(audit handler 后注册)。pi 同一 event 多 handler 按注册顺序串行调用,前者返回 { block: true } 后,后者不再触发。这意味着 SIEM 上看不到"试图写代码但被拦截"的痕迹 — reviewer 在 CI 里 LLM 想 write 一个文件被拦,audit 流里就是空的,看不到尝试。 该顺序未在 registerCompliance 注释里明示,~是从源码调用顺序观察出的隐含行为~。 已记入 B2.1 reviewer S11 已知局限,后续修复方向: ① 调整 registerCompliance 内 register 顺序(audit 先注册); ② 或将 audit 升级为不可拦截的旁路(用独立 hook 接 raw event,不走 handler 链)。 若上游 pi 后续改变 handler 短路语义,该行为可能漂移,需重新验证。
