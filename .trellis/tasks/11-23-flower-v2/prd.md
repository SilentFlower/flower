# Flower v2 重构

## 目标

让企业服务和新的 Desktop 应用使用同一份 pi 核心。运行行为的改进在两个产品入口生效，本地桌面和企业进程各自管理身份、可用工具和工作资源。开发分支为 `v2`，起点为 Flower 的远程主分支 `origin/main@58141e90`，沿用当前工作目录。

## 交付范围

第一项交付是整理当前仓库的实体目录、构建入口和项目说明。在新布局中验证三个现有应用后，先将现有 pi 依赖升级到稳定版 1.6.0，再验证双宿主共用核心。

新 Desktop 与 Flower 采用同一仓库和源码读取范围。桌面应用位于 `apps/desktop`，共享核心位于 `packages/agent-runtime`。两端可以在同一份变更中验证核心接口。宿主职责和逐应用迁移顺序见[结构设计提案](design.md)。

现有八个 npm 工作区均使用公开 npm 分发，包括共享核心 `@flower-ai/agent-runtime`。根聚合包保持私有。先在目标 registry 提供 Reviewer 固定依赖的核心版本，再执行 Reviewer 发布前检查。

开源 `v2` 的桌面直接进入本地工作台。用户自行配置模型，选择目录后运行任务。`v2-company` 负责员工准入、公司模型及其授权策略。两版共用运行时契约和桌面界面组件。

## 当前依据

Flower 已从 pi 0.76.0 升至 1.6.0，评审入口使用 `piMain`，钉钉入口创建 `Agent` 并通过 Redis 恢复消息。QoneAgent 的桌面通过独立 Node 进程使用 pi 1.5.2。小仙通过 DSH/Cordis 驱动会话，已有 Windows 企业账号及 Excel 报告验收记录。三者提供版本兼容、桌面通信和业务验收的对照依据。

## 联合验收草案

- [ ] 目录整理子任务在共享核心开发前完成，工作区清单、开发命令和现状说明与落盘内容一致。
- [ ] 从企业入口和桌面入口分别完成一次含工具调用的任务，记录两个宿主所用的核心版本及工具结果。
- [ ] 两个身份同时执行任务时，各自的凭据、消息、工具权限和工作区遵循对应宿主授权。
- [ ] 取消执行后两个入口都能呈现最终状态。重新打开桌面会话能查看已完成的交付物。
- [ ] 接入的既有企业业务通过相应的兼容性用例。
